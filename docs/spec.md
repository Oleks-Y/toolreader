# toolreader: agent action viewer

Read-only viewer for what coding agents _did_ in T3 Code threads. Actions come first; words are optional.

## Scope

- Sources:
  - T3 Code's database `~/.t3/userdata/statev2.sqlite` (`state.sqlite` before T3 0.0.46) (override with `T3_DB`), opened read-only. Covers every provider T3 runs (Codex, Claude, Cursor).
  - Codex sessions that ran outside T3 (CLI, TUI, Desktop, `codex exec`), read through `codex app-server`: `thread/list` for discovery, `thread/read` with `includeTurns` for content. Items carry no timestamps, so each item's time comes from the first rollout line that mentions its id. Sessions T3 runs itself are hidden (matched through T3's resume cursors); subagent threads are not listed. If `codex` can't start, this source is simply empty.
  - The same Codex sessions straight from rollout files (`$CODEX_HOME/sessions/**/rollout-*.jsonl`), with no app-server: the `thread/read` result is rebuilt from the file's `item_completed` events, so entries are identical. Used by the ledger (e.g. in CI); the viewer still lists Codex sessions through the app-server.
  - Without a T3 database, the T3 source is empty instead of an error.
  - Claude Code sessions outside T3 are not read yet.
- Separate repo. Code borrowed from `~/proj/t3code` is copied with a source comment, never linked.
- Built with Effect: an `HttpApi` contract in `src/core/api.ts` shared by the server and a typed browser client. All T3 schema knowledge lives in `src/server/ThreadStore.ts`.
- Local only: the server binds `127.0.0.1`.

## Views

- **Sessions** (`#/`): all non-deleted threads grouped by project. Running threads are marked. Includes search by title.
- **Action viewer** (`#/t/<threadId>`):
  - **Swimlane** on top: one lane per action kind, failures in red. Idle gaps longer than 60s are compressed. Drag to filter the tree to a time range; click a dot to jump to its row.
  - **Tree** below: turn → phase → folded group → action. Every level collapses. Expanding an action shows its command, output and diffs.
  - **Switches** (saved in localStorage):
    - action kinds: read, search, edit, run, git, web, tool, agent
    - user prompts, agent notes, reasoning
    - failures only
    - fold reads
    - phase headers

## Rules

- Shell wrappers (`/bin/zsh -lc "…"`) are unwrapped. Chains (`&&`, `;`, `||`) are split and each part is humanized (`sed -n '1,260p' f` → `read f:1-260`). `cd` is dropped.
- Codex `commandActions` (read / search / listFiles) take priority over parsing. Claude Bash `description` is kept as a secondary label.
- Shell commands are classified by intent, never by toolchain: `setup` (installs/fetches), `build` (compile, typecheck, lint), `run` (dev servers, scripts, anything unrecognized), `test` (any test runner: `go test`, `vp test`, `cargo test`, `pytest`, …), plus `docker`, `git` (git/gh), `read`, `search`, `edit`, `web`, `tool` (MCP and other tools) and `agent`.
- Kind of a chain = strongest part: git > docker > test > build > run > edit > setup > web > agent > tool > search > read.
- Phases treat run/build/test/docker after an edit as verification.
- A failure is a non-zero exit, `is_error`, or status failed/declined. The exception is a search exiting 1, which means "no match".
- Phases per turn: explore until the first edit → edit → verify (the first run after edits) → fix (an edit after verify) → ship (a git/gh write after edits).
- Two or more consecutive successful read/search actions fold into one group.

## Expanded bodies

- Highlighting runs only when a row is expanded, and each language loads on first use (Shiki, through `@pierre/diffs`). The Shiki theme follows the viewer theme.
- Commands are shown without their `/bin/zsh -lc` wrapper. Heredoc bodies get their own language from what consumes them (`python3 - <<PY`, `cat > x.ts <<EOF`).
- Outputs: JSON is pretty-printed, diffs and ANSI colors are detected, single-file reads use the file's language, anything else stays plain.
- File edits render as language-aware diffs (`FileDiff`). Diffs are stored as valid unified hunks; oversized ones are cut by whole hunks (or by lines with corrected header counts). Claude/Cursor edits hide line numbers, because they only know the edited snippet.
- Agent notes, reasoning and subagent prompts render as markdown; collapsed ones fade after two lines. Local file links show as code.

## Proof-of-work artifacts

- A thread, a turn range (`--turns 3-5`, as numbered in the viewer) or a time range exports as one JSON file: `ProofArtifact` (`src/core/proof.ts`) = `formatVersion`, export time, toolreader version, git branch/HEAD/remote of the repo, scope, outputs included/omitted, redaction count, and the `ThreadView` the viewer renders.
- The CLI writes it to `<repo>/.agent-work/<branch>/` (repo defaults to the thread's working directory); the viewer's export links download the same file. `#/file` opens one offline, read-only.
- Outputs are included by default (they double the size: a typical turn is ~19 KB, ~6 KB in git) and can be dropped with `--no-outputs`. Every free-text field is redacted, and the home directory becomes `~`. Redaction errs toward over-redacting.
- It is a faithful record, not tamper-proof evidence.

## Commit ledger

- Goal: see what the agent did for each commit, e.g. for a PR's `main..HEAD`.
- Entries live on a separate `agent-ledger` branch with its own history, never in the code history: `commits/<sha>.json` (`LedgerEntry`, `src/core/ledger.ts`) and `patch-ids.json` (patch-id → sha). An entry (format 2) holds `links` (one per thread: role `coder|reviewer|committer`, `via`, the commit's files it edited, its history), `files` (each changed file once: `attributed`, `shared` or `untracked`) and `notes`. Format-1 entries (one thread, `match`) still decode, as one coder link; the branch is never rewritten for them. Sync runs by hand (`toolreader ledger sync`) or from a `pre-push` hook (`ledger hook install`); `--push` shares the branch.
- Sources (`--source`): `t3`, `codex-app-server`, `codex-rollouts`, or `auto` (T3 if its database exists, plus rollout files from `--codex-home`, default `$CODEX_HOME` or `~/.codex`). A missing source is an error only when asked for by name.
- Linking threads to a commit, sessions in the repo's worktrees, strongest first: an `Agent-Session` trailer naming the session (`codex:<id>`, `claude-code:<id>`, or a thread id; agents' ids map to T3 threads through V2 provider threads and V1 resume cursors); a SHA printed by `git commit` (`[branch abc1234] subject`), in every session that printed it; otherwise the latest successful `git commit` action that started up to 10 minutes before the commit time. With none of those, `--session <id>` (repeatable) ties the commit to the named session and `--match-sessions` to the one session in this worktree (not another worktree of the repo) that edited files and ended between the previous commit and this one ("session"); when several qualify, none is attached and the commit is reported as ambiguous. Then every other session in this worktree that edited the commit's files (absolute paths only inside its worktree) between the previous commit and this one links as `evidence`: edit tools' files and shell writes (`>`, heredocs, `sed -i`, `cp`, `mv`, `rm`), never reads or `git add`. A merge records no files and gets no evidence: its branch's commits carry their threads. T3 subagent threads keep their parent (`lineage.parentThreadId`). A commit nothing links is recorded with every file `untracked` and listed as "no agent history".
- Stacked PRs split from one long-lived branch get their commits long after the work, often from rebases, so the window since the parent and who ran `git commit` show only bookkeeping. `ledger sync --history-since <rev>` (where the work began, e.g. the stack's base) gives each commit, instead, every turn since that revision, in any worktree of the repo, that edited one of its files ("evidence"), each with its prompt; trailers still link. A file the split moved still counts: a path a session wrote that is gone from the commit names the one commit file of the same name. A file many branches touch (`package.json`, CI config) can bring in a thread from other work. `ledger site --range A..B --history-since <rev>` builds the page from that matching directly and writes nothing to `agent-ledger`: one page per PR of a stack, before or without a sync.
- Sync merges into the entry a commit already has: a thread found again keeps its strongest `via`, and a link with no history yet (asserted before sync) takes the history sync found. Nothing is removed; a second sync with the same input writes no commit.
- `ledger link|unlink|note|review` change one commit's entry on the local branch (`asserted` links). `review` names the session from `CODEX_THREAD_ID` or `CLAUDE_CODE_SESSION_ID` and records the SHA it reviewed; on any other SHA (found by patch-id after a rebase, say) the review shows as stale. An asserted coder's or committer's history is the thread's from the commit's parent through the commit; a reviewer's runs from the commit through now, and edits nothing of the commit. Links are one per thread and role (a coder can review its own commit); a new `link`/`review` replaces its link, and only `link` undoes an unlink. `hook install --commit` adds a `commit-msg` hook that writes the trailer inside an agent session on the final message (plain shell, `git interpret-trailers --if-exists addIfDifferent`; a message left empty still aborts; never fails the commit); `uninstall` removes both hooks when they are ours.
- An entry holds the history since that thread's previous commit action (or its start), up to the commit action. Leading discussion-only turns are dropped; a segment that starts mid-turn keeps the turn's prompt.
- After a rebase or amend that keeps the diff, `git patch-id --stable` finds the entry again (shown as "found by patch-id").
- Outputs and redaction work as for proof-of-work artifacts; the thread title (the first prompt line) and labels are redacted too, like every other free-text field. Each output is then clipped to `--max-output` bytes (default 8192, head and tail, `0` keeps it): the action records the bytes cut (`clipped`) and the viewer says so. The viewer's outputs are already 1500 + 1500 characters at most, so the default rarely cuts.
- `--push` fetches `agent-ledger` from origin, writes the new commit on top of the remote tip (merging in local-only entries), pushes, and moves the local branch only once the push lands. A push that loses a race refetches and rebuilds, up to 5 attempts. Never touches HEAD or the working tree.
- Sync refuses to run while a worktree has `agent-ledger` checked out: moving the ref would move that worktree's HEAD and leave its files behind.
- The `pre-push` hook reads every pushed ref first, then syncs each branch pushed to origin (`remote..local`, or `local --not --remotes=origin` for a new branch) with `--push`. When the push carries `agent-ledger` itself, it syncs locally only (a nested push would make git reject that ref, and an `--atomic` push whole). Ledger trouble only warns; it never stops the push. `hook install` is idempotent and replaces or removes only a hook byte-identical to the one it writes; anything else (another hook, or ours edited) is left alone, with the lines to add printed instead.
- `ledger site --range A..B --out DIR` writes `DIR/index.html`: the ledger page (`LedgerPage` with `inline`) on that range, read from the local `agent-ledger` branch. What it shows goes through `publicRange`: every free-text field redacted again (commit subjects come straight from git), the repo named by the remote's owner/name or its directory, and its path written as `.` wherever session text mentions it; `ledger show` and `sync` print the same. Markdown images in session text render as links, here and in the live viewer, and the page's CSP (`default-src 'none'`, the script by hash, `img-src data:`) blocks any load that slips through. One file with the viewer inlined as a classic script and the range as JSON (`<` escaped), because Chrome blocks module scripts and chunk loads from `file://`. Read-only (no repo form, labeling or export); the theme picker works. It is about 11 MB, nearly all Shiki grammars; trimming them is possible but risks `FileDiff` asking for a language that is gone.

## Checkpoints

- Goal: keep what an agent did once it happened, with what the ledger drops (model, token usage, timing), before the session's own store changes or is deleted. Private, beside `agent-ledger`: a commit checkpoint maps to a ledger link (`toLedgerEntry`), so the ledger can later be built from Postgres.
- A checkpoint (`src/core/checkpoint.ts`, `formatVersion` 1) is one thread at one moment: `trigger` `commit` (one link of a commit: role, via, the commit's files and the ones this thread edited) or `manual` (the whole session). It holds the thread (as a ledger link has it), the provider's session name, the repo (origin's owner/name, branch, HEAD), entries and labels redacted and clipped exactly like a ledger link's, per-turn summaries (prompt id, start/end, model, token usage as the provider reported it, phases with their action ids, stats), files touched and duration. No images: they are not stored.
- Token usage is a snapshot of the context window after a turn's last request (T3's `tokenUsage`), so turns are never summed.
- Postgres (`TOOLREADER_DATABASE_URL`, migrated on start), every key led by `workspace_id`: `workspaces`, `api_tokens` (only each token's SHA-256), `checkpoints` (the JSON as jsonb, with `trigger`, `thread_id`, `session`, `repo`, `commit_sha` and `patch_id` generated from it, plus who uploaded it and with which client version) and `commit_rewrites` (git's old → new SHAs after an amend or rebase). A commit's checkpoints are found by SHA, then by a recorded rewrite, then by patch-id. The CLI uploads through the backend (below); with no backend configured and `TOOLREADER_DATABASE_URL` set, it writes straight to the database, into workspace `local` with no token.
- Every command that opens the database migrates it first. It refuses a database a newer toolreader migrated, and it refuses a checkpoint in a newer format. Both errors say to upgrade toolreader. How to add a migration or a format: `AGENTS.md`.
- The connection is a CLI's: `application_name` `toolreader`, a pool of 2, 5 s to connect, and 30 s per operation. An operation that runs out of time is cancelled on the server, so the limit holds behind a transaction-mode pooler, which refuses `statement_timeout` at connect. Migrations wait at most 10 s for the migrations table's lock. The URL is read as a redacted value and is never logged.
- The id is the key (`commit:<repo>:<sha>:<thread>:<role>`, `manual:<thread>:<last entry id>`), keyed by the resolved thread, so any name of the session gives the same id. Taking it again stores nothing; `--replace` overwrites only content that changed.
- `toolreader checkpoint put --session ID [--repo PATH] [--replace] [--max-output BYTES] [--no-outputs]`.
- `toolreader checkpoint collect (--range A..B | --pr N | --sha X) [--repo PATH] [--source …] [--session ID … | --match-sessions] [--replace] [--max-output BYTES] [--no-outputs]` stores commit checkpoints for a scope, which it requires: it never sweeps every session. Its links are exactly `ledger sync`'s (`linkCommits`, same sources and flags), one checkpoint per (commit, thread, role), holding only the window the link names. Threads the commit's local `agent-ledger` entry lists as `unlinked` are skipped. `--pr N` reads base and head with `gh pr view`, fetches `pull/N/head` when the head isn't local, and takes evidence from the worktree whose HEAD is the PR head (else the one it runs in). `--sha X` is that one commit. Subagent threads of a linked session are not taken. Border rules: [`docs/design/checkpoint-scope.md`](design/checkpoint-scope.md).
- Sessions in the commit's worktree that no link takes but whose window shows a signal (a shell write, `git add`, a script naming a commit file, …) are printed as candidates and not stored; a person links one with `ledger link`. An AI relevance judge for them is deferred.
- The client (`src/server/checkpoints/BackendClient.ts`) reads `backend.url`, `backend.token` and `backend.workspace` from `~/.toolreader/config.json`, so hooks work without the shell's environment; `TOOLREADER_BACKEND_URL`, `_TOKEN` and `_WORKSPACE` override them. The URL must be `https://`, or `http://` to this machine only. Before its first upload a run checks `GET /v1/meta` (cached an hour in `~/.toolreader/cache/meta.json`) and stops at "upgrade toolreader to ≥ X" below `minClient`. Each record first passes the backend's own checks (`admitCheckpoint`) on the client, so one the backend would refuse, an unredacted one included, never leaves the machine. Records go one per request, with `Authorization`, `Toolreader-Client` and `traceparent`. Only what no later run can fix drops a record (`413`, `411`, a per-record rejection), and it is reported. Anything else (unreachable, 30 s without an answer, 5xx, 429, a refused token, an old client, an answer that isn't the backend's own, such as a proxy's page) queues the record, already redacted, in `~/.toolreader/outbox/` (`0600` files in a `0700` directory, one per record and backend), and every `put` and `collect` sends what was queued for the configured backend and workspace first. A failure of the backend as a whole (unreachable, slow, failing, a refused token, an old client) stops that and says why and where; one request's odd answer keeps only that entry back. A record that went out directly removes an older queued copy of it. Queued records go through the same checks as new ones before they leave. An outbox file that isn't JSON moves to `outbox/unreadable/`; one another toolreader version or backend queued is left alone and counted. A repo without an `origin` remote can't upload: the backend names repos `owner/name`.
- `toolreader checkpoint rewrite [--repo PATH]` sends git's `old new` pairs from stdin (what `post-rewrite` gets), up to 1000 per request, and nothing else: an amend is commit time, so the outbox waits for the push.
- Hooks (`src/server/checkpoints/checkpointHooks.ts`) act only in a repo that opted in: `toolreader checkpoint hook install [--repo PATH]` writes `pre-push`, `post-rewrite` and the ledger's `commit-msg` (`Agent-Session` trailer; someone else's `commit-msg` is kept, with a warning), then sets `git config toolreader.checkpoints true`; `hook uninstall` unsets it first, then removes the three. Each hook is written with a hash of its script, so an upgrade replaces a hook no one edited, and an edited hook, or the ledger's, is left alone. Elsewhere the git hooks exit in shell, before Node starts. Nothing is sent at commit time. `pre-push` (origin only, branches only) works out what each pushed branch adds while the push still waits (commits on none of origin's branches nor in what a force push replaces, written as a few boundary SHAs), then one detached job waits for git to finish, asks origin itself whether it took each branch (`git ls-remote` on its push URL, with prompts off; tracking refs miss single-branch clones, and a hook manager's wrapper can exit before git does), and runs `checkpoint collect --range <range> --hook` for each branch it took, one after another: the push never waits, and a refused push (branch protection, secret scanning) uploads nothing and is logged as skipped; `post-rewrite` starts `checkpoint rewrite --hook` the same way. With `--hook` a command reports to `~/.toolreader/checkpoint.log` (crashes included), never to stdout, and never fails; past 1 MB the log moves to `checkpoint.log.1`.
- `toolreader checkpoint hook stop` is an agent's Stop hook (Claude Code's JSON on stdin, or Codex `notify`'s as its argument; `hook install` prints both snippets). In an opted-in repo it appends one line (session, transcript path, cwd, turn id, time) to `~/.toolreader/pending.jsonl` and sends nothing. Nothing reads that file yet: it is there to find a push's sessions without scanning every session store, once scanning is slow.

## Checkpoint backend

- A versioned HTTP API in front of the checkpoint database (`src/core/backendApi.ts`, `src/server/backend/Backend.ts`). It owns Postgres and its migrations; clients send only redacted records.
- `toolreader backend serve [--port N]` serves `/v1` on `127.0.0.1` (default port 4780), with a pool of 10 on `TOOLREADER_DATABASE_URL`. `toolreader backend token create --workspace SLUG --name NAME` creates the workspace if it is new and prints a token once (`trk_…`); the database keeps only its SHA-256.
- Every request but `GET /v1/health` needs `Authorization: Bearer <token>`: 401 without a live token, 403 when the path's workspace isn't the token's. Checkpoint endpoints also need `Toolreader-Client: <version>`: 426 with `minClient` when it is missing or older. `GET /v1/meta` reports the API version, `minClient` and the checkpoint formats taken.
- `POST /v1/workspaces/:ws/checkpoints` takes 1–100 records, at most 8 MB per request (413; a body needs a `Content-Length`, else 411) and 2 MB per record. Each record is checked on its own (`admitCheckpoint`): a known `formatVersion`, a valid record, finite numbers, an ISO `takenAt`, no NUL in its id, an id equal to its `checkpointKey`, commit set exactly for `commit` checkpoints, and no string or key the redactor would still change (it knows the backend's own `trk_` tokens). A record that fails is a `rejected` line naming the reason and the field (label keys as `*`), never the text; the others are stored as `inserted`, `exists`, `differs` or (with `replace=true`) `replaced`.
- Reads: one record by id, a commit's records (`/repos/:repo/commits/:sha/checkpoints?patchId=`, repo as `owner%2Fname`, at most 50), a thread's records a page at a time (`?limit=` up to 50, `&after=` the last id of the page before); `POST …/repos/:repo/rewrites` records amend and rebase pairs. All of it stays inside the token's workspace.
- The server writes no request log (URLs name repos and threads), and a database failure answers 503 with a fixed message.
- A request with a W3C `traceparent` continues the caller's trace. There are no custom metrics: each request's server span carries its route template (`http.route`), method and status, and its duration is the span's, so rate, errors and latency come from spans downstream. The upload's span (`Backend.put`) counts its records by result (`result.inserted`, …) and by rejection reason (`rejected.not-redacted`, …), zeros included. URLs, headers and client addresses are dropped from every span (`keepAttribute`); records' ids and text never reach one.

## Tracing

- Every command can be traced, to a file, to an OpenTelemetry collector, or both (`src/server/Trace.ts`). Nothing is traced unless asked.
- `TOOLREADER_TRACE=trace.md` writes the run's spans when it exits, as two Mermaid diagrams: when each step ran, and which step called which. It keeps at most 20,000 spans.
- Spans go to a collector over OTLP/HTTP only when both `OTEL_TRACES_EXPORTER=otlp` and `OTEL_EXPORTER_OTLP_ENDPOINT` (or `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`) are set, as `service.name` `toolreader`, or what `OTEL_SERVICE_NAME` says (`toolreader-backend` for the backend, so a collector tells the two apart). Requiring both means an endpoint set for other tools sends nothing. Effect's own exporter does the sending, with no OpenTelemetry SDK, and adds about 90 KB to the bundle.
- `TOOLREADER_TRACE_LEVEL` sets the granularity. `commands` keeps one span per command (`toolreader checkpoint put`), or one per request under `serve`. `steps` is the default: it adds every service step (`Checkpoints.take`, `CheckpointStore.put`, migrations). `all` adds each SQL statement.
- Spans hold ids, counts, results and parameterized SQL, plus the database's host and port. They never hold session text, the database URL, parameter values, request URLs or headers. A failed span keeps only its error's tag, because messages and stacks can quote session text or paths. Logs don't become span events.
- There are no metrics: `Checkpoints.take` spans carry the result and the duration, which is what a take counter would count.
- A local viewer: `docker compose -f docs/observability/compose.yml up -d` runs Jaeger with its UI on http://127.0.0.1:16686 and OTLP on 127.0.0.1:4318. A client's run and the backend requests it makes are one trace (`traceparent`), so a hook's background upload can be read step by step after it ran. The user stories and their recorded demos: [`docs/design/checkpoints.stories.md`](design/checkpoints.stories.md).

## Packaging

- One `toolreader` bin (`src/server/bin.ts`): `serve`, `ledger sync|show|site|hook`, `export`, `checkpoint put|collect|rewrite|hook`, `backend serve|token create`. `vp pack` bundles it with every dependency to `dist/bin.mjs`, as t3code does, because Node does not strip types under `node_modules`; the package ships only `dist/` and installs no dependencies. It stays private: install it from `npm pack`'s tarball.
- The composite action (`action/`) installs that tarball, or packs a toolreader checkout, and runs `ledger sync` or `ledger site`; `docs/ci/` has the example workflows.

## Codex labels (on demand)

- A "Label with Codex" button on each turn sends that turn's non-trivial actions and fold groups to `codex exec --output-schema`, run read-only and ephemeral.
- It uses the model and reasoning effort from T3's `textGenerationModelSelection` setting (default `gpt-5.6-luna`, `low`).
- Labels are cached in `~/.toolreader/labels.json` and never written to T3.

## Live updates

- While a thread is running, the viewer polls a cheap head endpoint (`/api/threads/:id/head`) every 3s. It re-fetches the full thread only when the head changes.
