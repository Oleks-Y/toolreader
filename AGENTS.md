# toolreader

Read-only viewer for what coding agents _did_ in T3 Code threads. It reads T3's SQLite database and shows each thread as a swimlane plus a turn → phase → action tree. Design notes live in `docs/spec.md`.

Setup, libraries and conventions are copied from `~/proj/t3code`. When in doubt, do what t3code does.

## The ways to hurt yourself

1. **Writing to the live T3 install.** `~/.t3/userdata` is the developer's real T3 database, in use while you work. toolreader opens it read-only, and it must stay that way. Never open it read-write, never run migrations against it, never "clean it up". For experiments, snapshot it (see Test data) and point `T3_DB` at the copy.
2. **Killing by pattern.** Never `pkill -f`, `pgrep | kill`, or kill a PID found by matching a name. Kill only a PID you captured at spawn, or the owner of your port from `lsof -nP -iTCP:<port> -sTCP:LISTEN` after confirming its cwd is this repo.
3. **Binding beyond localhost.** The server exposes every agent session on the machine. It binds `127.0.0.1`; keep it that way.

## Where code lives

- `src/core`: browser-safe code shared by server and web.
  - `domain.ts`: Schema domain models (Action, Message, ThreadView, …).
  - `api.ts`: the `HttpApi` contract. Server and client both derive from it; never put server code here.
  - `payload.ts`: Schemas for T3's raw activity payloads, for every provider.
  - `normalize.ts`, `shell.ts`, `tree.ts`: pure transforms, from raw rows to entries to tree.
  - `codex.ts`: turns Codex `thread/read` items into the same T3-shaped rows.
  - `t3v2.ts`: turns T3's orchestration V2 turn items into the same rows. T3 0.0.46 nightlies write `statev2.sqlite`; its V1 tables stay, frozen at the upgrade, and still hold V1 threads' tool calls (V2 imports only their messages, under `migration:v1:` ids, which are skipped).
  - `rollout.ts`: scans rollout files for item timestamps and for the tool calls `thread/read` drops (it rebuilds items only from `item_completed` events, which most rollouts keep for messages alone), as app-server items. `shellJoin` quotes argv exactly as Codex does (Rust `shlex`).
  - `claudeTranscript.ts`: turns a Claude Code transcript (`~/.claude/projects/<dir>/<session>.jsonl`) into the rows T3 V1 stored for Claude (`data: { toolName, input, result }`), pairing each `tool_use` with its `tool_result`, so `normalize` needs nothing new.
  - `sanitize.ts`: what published data (the site's demo, `scripts/privacyGate.ts`) may carry off the machine. Paths in home directories outside the repo, emails and local names become placeholders (`anonymize`) or take their field, message or action with them (`remove`). `privacy.ts` is the website's publication check; both use its path and email patterns.
  - `rolloutThread.ts`: rebuilds the `thread/read` result from a rollout file alone (its `item_completed` events, mapped from the core's snake_case shapes to the app-server's camelCase), so sessions read without `codex app-server` give the same entries. `src/server/CodexRollouts.test.ts` pins this against a real `thread/read` capture (`src/server/fixtures/`).
  - `coverage.ts`: the files a linked session was seen reading for a commit (`readsFor`), stored on each link and listed on the history page; not listed means not seen read.
  - `checks.ts`: the tests and builds behind a commit link (`checksFor`): each one a linked session ran from its first linked turn (its first turn, for a trailer link) up to the commit, its outcome, what that rests on (exit code, error flag, nothing; `|| true` makes it unknown) and how many of the commit's lines were written after it, matched by content like linking. `history sync` stores them on each link; the history page shows each link's last test and build. `audit.ts`: what a repo's sessions recorded, counts only (`history audit`). `insights.ts`: Project Insights' two detectors (`detect`: recurring failures by a normalized signature, files read and never edited, both across independent sessions, a subagent counting with its parent) and the findings lifecycle (`TRANSITIONS`).
- `src/server`: Effect services and the HTTP server.
  - `ThreadStore.ts` is the **only** module that knows T3's table layout. If T3 migrates, fix it there. It reads V1 tables alone (`state.sqlite`, older T3) or V1 and V2 together (`statev2.sqlite`), by whether the V2 tables exist.
  - `Labeler.ts` runs `codex exec` and caches labels in `~/.toolreader/labels.json`.
  - `CodexSessions.ts` lists and reads Codex sessions that ran outside T3, through a long-lived `codex app-server` process. Sessions T3 owns (its resume cursors) and subagent threads are skipped.
  - `CodexRollouts.ts` does the same straight from `$CODEX_HOME/{sessions,archived_sessions}/**/rollout-*.jsonl` (listing reads only each file's first line), for when there is no T3 and no app-server, e.g. CI after `codex exec`. Without a T3 database, `app.ts` provides `ThreadStore.empty` instead of failing.
  - `ClaudeTranscripts.ts` lists and reads Claude Code sessions run outside T3 (CLI, desktop app, other SDK hosts) from `$CLAUDE_CONFIG_DIR/projects` (default `~/.claude`), ids `claude:<sessionId>`. Listing reads each file's first 50 lines; sessions T3 runs (`ThreadStore.claudeSessionIds`: V1 cursors' `resume`, V2 provider threads' native ids) are skipped. Subagent transcripts (`<session>/subagents/agent-<id>.jsonl`, ids `claude:agent-<id>`) are left out of `list`, which the viewer shows, and listed apart by `subagents`, with their parent, for `history sync`; both readers do this.
  - `NodeSqliteClient.ts` is copied from t3code. Re-copy it rather than editing it.
  - `bin.ts` is the one `toolreader` CLI: `serve`, `export` (`export.ts`), `history` (`history/historyCli.ts`) and `backend` (`backend/backendCli.ts`). `vp pack` bundles it, with every dependency, to `dist/bin.mjs` (Node won't strip types under `node_modules`); the viewer builds to `dist/client` and the history page template to `dist/site`. `ServerConfig.distDir` finds `dist` from either the bundle or `src/server`. `app.ts` is the service wiring the commands share.
  - `Sanitizer.ts` gives `core/sanitize.ts` its rules (this machine's names, the repo's `.toolreader.json`) and runs the optional agent pass: `acp.ts` prompts an ACP agent (`codex-acp`, gpt-6-luna) over stdio through the Codex app-server protocol client, adding the `"jsonrpc"` field ACP needs and refusing every permission request. Tests use a fake ACP agent (`Sanitizer.test.ts`) and `Sanitizer.off`; never call the real one from tests.
  - `Proofs.ts` builds proof-of-work artifacts (`core/proof.ts`: schema, scope selection, redaction).
- `src/codex-app-server`: t3code's Codex app-server client, copied. Its `README.md` lists the two local edits to re-apply when re-copying.
- `src/core/ledger.ts`: the page's data (`LedgerRange`: commits, each with an entry of linked threads and their redacted history) and `buildEntry`; `ledgerSite.ts` makes a range public (`publicRange`) and fills the page template.
- `src/core/history.ts`: which agent turns wrote a commit, by content (`linkByContent`; `history sync` no longer links by it, only by declarations and trailers): a turn is linked when lines its edits added are lines the commit adds that its parent didn't have. Time, worktree and file names don't matter, so commits made long after the work (stacks split from one branch, rebases, squashes) still find it. `historyRecord.ts`: what is stored and sent: `ThreadRecord` (a thread's whole history, redacted) and `CommitRecord` (a commit's links to threads).
- `src/server/backend/`: the history backend. `HistoryStore.ts` is the only module that knows its Postgres tables (`Migrations/`, applied on start by `PgMigrations.ts`): `workspaces`, `api_tokens` (SHA-256 only), `threads`, `commits` and `blames` (migration 4: Jev's answers per hunk and model, `core/blame.ts` `StoredBlame`), every key led by `workspace_id`. A thread is replaced when its history changed, a commit's links whenever it is linked again. Tests run against a real Postgres per test file (`testPostgres.ts`: Docker, or `TOOLREADER_TEST_PG_URL`). `Backend.ts` serves `core/historyApi.ts` (`/v1`: thread hashes, `PUT` a thread, `PUT` a commit's links, reads; `BrowseApi` for the webapp: repos, a repo's ledger newest first, stored blame) on 127.0.0.1, one workspace per bearer token; every record is checked again there (`historyRecord.ts` `admitThread`/`admitCommit`: format, schema, redaction) and refused with a 422 that names fields, never text. `backendCli.ts` is `toolreader backend serve` and `backend token create`. `GitHub.ts`: a person signs in with GitHub (`history login`, device flow through `TOOLREADER_GITHUB_CLIENT_ID`): `Backend.ts` lets them into a workspace that lists their login (`members`, migration 2; `backend member add`) and into a repo only when GitHub, asked with their own token, says they can read it (cached a minute). A sign-in names the repo on every read and never writes history: syncing stays with `trk_` workspace tokens. Tests use a fake `GitHub` layer or a fake HTTP client; never call GitHub. Insights findings live in `findings` (migration 6): a detector run (`detect`) refreshes a finding's evidence, never its status (except that sessions after a rejection propose it again, `insights.ts` `reopenReason`), and each status change keeps who, when and why; people's corrections to a finding's members are `findings.corrections` (migration 7); `submit` keeps an agent's own finding (`agent`, with who submitted it) only when every citation reads back from the repo's threads and its quote is in that entry (`insights.ts` `findQuote`: spacing, case and colors aside; kept as the entry has it, which is what the citation marks; 409 naming those that fail); it lands as `detected`, and the same subject (`insights.ts` `submissionKey`) again updates its evidence. `search` reads `entries` (migration 5: one row per stored entry, its searchable text under a pg_trgm index, rewritten in the thread's own transaction and removed with it), optionally only threads linked to one commit (SHA or prefix) and only actions of some kinds (`ACTION_KINDS`); without text it lists the newest entries those filters keep. `evidence` reads a citation back (thread, entry, version) or says why not: version-unavailable, withheld, deleted, expired, missing. Removal (`backend thread delete`, or expiry past `TOOLREADER_RETENTION_DAYS`, swept hourly by `backend serve`) takes a thread's body, search hits and findings' citations and leaves a marker in `removed` (migration 3), so its citations read `deleted`/`expired` and a deleted thread is never stored again. `backend token revoke`, `backend member add|remove`. `docs/github-app.md` is the App's setup; `searchBench.test.ts` (opt-in, `TOOLREADER_BENCH=1`) the search benchmark, its last run in `docs/benchmark.md`.
- `src/server/RepoSessions.ts`: every session, from the chosen sources (T3, Codex rollouts or app-server, Claude transcripts), subagents included, that worked in one of a repo's worktrees, read whole; the ones that couldn't be read are listed as `unread`, and `history sync` reports them. `history sync` reads sessions through it.
- `src/server/history/`: the CLI side of history. `HistorySync.ts` is `toolreader history sync --range|--pr|--sha`: it reads the range's commits (each one's added lines that its parent's tree didn't hold, streamed through `git grep -e ""`), links them through what agents declared (`history link`) and `Agent-Session` trailers (matching content alone links nothing), and sends each linked thread whole (only when its content hash differs from the backend's) and then each commit's links. `--dry-run` links and reports without sending. `HistoryClient.ts`: the backend's settings (`backend.{url,token,workspace}` in `~/.toolreader/config.json`, or `TOOLREADER_BACKEND_*`; plain http only to this machine) and its typed client. `history site --range|--pr` reads the range's commit links and threads back from the backend and writes the ledger page (`core/historyPage.ts` `historyRange`: each link shown as its episode, the linked turns and the short runs between them, with a note of how many of the commit's new lines its agents wrote), through `publicRange` and the `dist/site` template. `declareCli.ts` is `history turns|link|unlink`, what agents run to declare their own links (`core/declare.ts`: parsed back from session histories by `history sync`, applied over matching); `historySkill.ts` is what makes them: `history skill install [--commit]` writes the skill to `.claude/skills/toolreader-history/` (with an `.agents/skills/` link), a sealed rule block in `AGENTS.md` and `CLAUDE.md` (once when one links to the other), and a `PostToolUse` hook on Bash, in `.claude/settings.json` (Claude Code) and `.codex/hooks.json` (Codex, which runs it once approved with `/hooks`), that runs `history remind` (`declareCli.ts`: a reminder in context after a `git commit`). Each part is sealed or recognized, so upgrades replace ours and edited ones are left alone; `--commit` commits only those paths, skipping any that had other uncommitted changes. `history hook install` only points to it when the skill is missing. `historyHooks.ts` is `history hook install|uninstall`: the opt-in (`git config toolreader.history`), a `pre-push` hook whose one detached job asks origin (`git ls-remote`) whether it took each branch before running `history sync --hook`, and a `commit-msg` hook that adds an `Agent-Session` trailer inside an agent session. Hook files carry a hash of their script, so an upgrade replaces ours and an edited one is left alone. Hooks report to `~/.toolreader/history.log` (rotated at 1 MB) and never fail; a range that failed waits, one file per range in `~/.toolreader/pending/` keyed by the repository's common git dir, for the next hook in any of its worktrees. `scripts/smoke.sh` runs the packed tarball end to end (backend, a session that wrote a file, a push); CI runs it. The diff a viewer gets is clipped (`normalize.ts` `clipDiff`); a clipped diff keeps every added line as `addedKeys` for matching, which never leaves the machine.
  - `history insight submit --subject --pattern --suggestion --cite "THREAD#ENTRY@VERSION :: quoted text"…` (what an agent runs after its own investigation with `history search` and `history show`; no model runs in toolreader), `history insight members` (a person's corrections to a finding's sessions), `history show THREAD#ENTRY@VERSION` (a citation read back), `history insight sample|score` (`core/insightsEval.ts`: findings to label, a fixed dev/held-out split, precision, novelty, recall from `missed` rows, agreement), `history search [TEXT] [--commit REV] [--kind KIND]…` (this repo's threads on the backend, or `--all`; one commit's, actions of some kinds), `history insights` and `history insight propose|accept|reject|modify|implemented|monitor|evaluate ID --why` (Insights on the backend), `history login` (`githubLogin.ts`: the device flow; the token goes to `backend.githubToken`, beside the workspace token) and `history audit`. Reads go as the GitHub sign-in when there is one (`backendSettings("reader")`). Each thread record carries its `snapshot` (a versioned manifest, each field `recorded`, `derived`, `conflicting` or `unavailable`: how the session started, from the native files: T3 sessions get theirs from their Codex rollout or Claude transcript, found by native id) and `origin` (reader, file relative to the provider's home, SHA-256 of the bytes read). The backend names a repo by `ledger.ts` `repoKey`: `owner/name` on github.com, `host/owner/name` elsewhere.
- `src/app`: the history webapp, on TanStack Start with TanStack Query (`vite.app.config.ts`; `vp run app:dev`, `app:build` to `dist/app`). An organisation's repos with agent history, each repo's ledger and PRs with agent history, a PR's or commit's history (`historyRange`, rendered by `web/LedgerPage.tsx` `LedgerCommits`), and blame from a pasted GitHub diff line link (`server/blame.ts`: GitHub's GraphQL blame finds the commit, the backend its threads, Jev the pieces; `web/BlamePage.tsx` `BlameView` renders it). Search (`routes/$owner.$repo.search.tsx`) finds entries in the repo's sessions through the backend's `search`, narrowed to one commit's sessions (the commit page links there) or to operation types (the viewer's action kinds, in their colors), and shows the entry each hit cites through `evidence`, or why it can't be read. Insights (`routes/$owner.$repo.insights.tsx`, `findings.ts`) lists the repo's findings by where they are in the lifecycle and lets a person run the detectors and take the next step with a reason; these calls go to the backend as the person's own GitHub sign-in, so each decision is kept under `github:<login>` and the backend must list them as a member (`backend member add`). Modifying a finding isn't offered there. Unlike `src/server/Blame.ts` it needs no clone and no local sessions. People sign in through the GitHub App's user authorization; every server function (`fns.ts`) reads the session, and every repo read checks GitHub lets that user read the repo (`server/history.ts` `mustRead`). Tokens (backend, GitHub, TypeSafe) stay in `src/app/server`, which `fns.ts` imports only inside handlers, so no server module reaches the browser. The App asks for read access only: metadata, contents, pull requests. `GITHUB_DEV_TOKEN` (e.g. `gh auth token`) signs in without the App, outside production.
- `src/web`: React UI. Calls the server only through the typed client in `client.ts`.
  - `code.tsx`: syntax highlighting for expanded bodies, as t3code does it: Shiki through `@pierre/diffs`' shared highlighter, `FileDiff` for file diffs, `react-markdown` for notes, where images render as links (session text is untrusted, and an image loads by itself). `codeLang.ts` picks the language (pure, tested).
  - `FileDiff` virtualizes against the window scroll: never put it inside a scroll box, or it renders blank.
  - `LedgerPage.tsx` is the static history page (`site.tsx`, what `history site` writes): each commit's links rendered through `ActionView` with `view` + `embedded` (read-only: no labeling or export), from the range inlined in the page. It never calls a server.
  - `vite.site.config.ts` builds `site.tsx` into one HTML file with a classic inline script: Chrome blocks module scripts and chunk loads from `file://`. Its CSP lets only that script run (by hash) and nothing load (`img-src data:` only). Never add anything the page fetches (fonts, chunks, workers); `src/server/siteTemplate.test.ts` checks the template and its CSP, and `src/web/site.test.tsx` that session text can't add an image.
- `oxlint-plugin`: custom lint rules copied from t3code.
- `scripts/themes.py` generates `src/web/themes.css` (six themes, one hue per action kind) and fails if any two kinds get too close in color. Edit the script, never the CSS; re-run it with `python3 scripts/themes.py`.

## Taste

- Effect: read `~/proj/t3code/.repos/effect-smol/LLMS.md` before writing Effect code, and follow it. Use `Effect.fn("Name")`, services via `Context.Service` with a static `layer`, errors via `Schema.TaggedErrorClass`, and Schema (never hand parsing) for anything untrusted.
- Imports use namespace subpaths (`import * as Effect from "effect/Effect"`). Barrel imports are a type error.
- Hoist Schema decoders and encoders to module scope (`toolreader/no-inline-schema-compile`).
- Pure logic stays pure. `core/` functions take data and return data; Effect lives at the edges (server, client).
- Provider payloads vary wildly. Payload schemas keep every field optional and nullable, and a payload that fails to decode degrades to an untyped row instead of dropping the thread.
- Comments say how a thing is used, not what each line does.

## Test data

An empty database is a bad test. To run against realistic data without touching the live one:

```bash
rm -rf .t3 && mkdir .t3
node -e "new (require('node:sqlite').DatabaseSync)(process.env.HOME + '/.t3/userdata/statev2.sqlite', { readOnly: true }).exec(\"VACUUM INTO '.t3/statev2.sqlite'\")"
T3_DB=$PWD/.t3/statev2.sqlite PORT=4778 vp run start
```

`VACUUM INTO` is safe while T3 has the source open. A plain `cp` without the `-wal`/`-shm` files gives a corrupt copy.

## Verifying

- Run the smallest proof first: `vp test run <files>` for the tests you touched, then `vp check` (format and lint) and `vp run typecheck`. `vp run build` builds the viewer, the site template and the CLI bundle.
- Packaging changes: `npm pack`, install the tarball into a temp directory, and run `toolreader` from there.
- Changes to server behavior ship with focused tests. `ThreadStore` tests seed an in-memory SQLite database, and `Labeler` tests use a fake `codex` binary. Follow those patterns, and never call the real Codex from tests.
- Changes to normalization should also be run against the real data shape (a snapshot, as above), because providers emit payloads the unit tests don't cover.
- For UI changes, use the `test-toolreader` skill. Ask before opening browsers.

## Commits and PRs

- Conventional commit titles in plain language, e.g. `fix(viewer): failed searches no longer fold`.
- One concern per commit or PR. Pre-commit formats staged files (`vp staged`); CI runs check, typecheck, test and build.
